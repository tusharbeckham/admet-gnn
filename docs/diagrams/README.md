## 1. Why this file exists before any diagram does

Sixteen diagrams drawn over fifteen weeks, in four different tools, by one person
who will have forgotten by week nine what colour meant "external system" in week
two. The result of not writing this file is a report where the same component is a
blue rectangle on one page and a grey cylinder on the next, and an assessor who
cannot tell whether that means something.

So: the inventory is fixed here first, the tool per diagram is assigned here, and
the visual vocabulary in §4 is decided once. **A diagram that breaks §4 is wrong
even if it is accurate.**

The second reason is scheduling. A diagram is not a five-minute job, and sixteen of
them discovered in the last week is how a report ends up with three. Each row below
carries the increment it belongs to, so they arrive spread out.

## 3. Tool assignment, and why each

| Tool | Used for | Reason |
|---|---|---|
| **Mermaid** (`.mmd`) | sequence, class, ER, flowchart | Text source, so it diffs in git and a reviewer can see what changed. Renders in GitHub without a build step. |
| **Excalidraw** (`.excalidraw`) | C4 context / container / component, GNN, deployment | Boxes-and-arrows work where hand placement carries meaning. The file is JSON, so it is at least versioned, even if the diff is unreadable. |
| **matplotlib** (`.py`) | every chart of measured data | Reproducible from `results/`. Also the only option that can be re-run at submission time to prove the figure matches the data. |
| **RDKit** (`.py`) | molecule depictions, attribution overlays | It is already the chemistry oracle (A-2 in the SRS); a second renderer would be a second source of truth about a structure. |

Not used, and why: PlantUML (another toolchain for what Mermaid already does),
draw.io (its `.drawio` XML diffs no better than Excalidraw's JSON and it is one more
install), PowerPoint (produces raster output at the wrong resolution and cannot be
regenerated).

## 4. Consistency rules — the visual vocabulary

Decided once, here. Every diagram obeys all nine.

| Rule | The standard |
|---|---|
| 1. Shape means layer | Rectangle = software this repo owns. Rounded rectangle = external system. Cylinder = datastore. Person icon = human actor. Nothing else. |
| 2. Colour means ownership, never importance | `admet-core` and its callers: one fill. External: grey. Datastore: a third. **No red for "important"** — colour is a legend entry, not emphasis. |
| 3. Arrow direction is dependency or message, and the diagram says which | On a static diagram an arrow means "depends on". On a sequence diagram it means "sends". Never both in one figure. |
| 4. Every arrow is labelled | An unlabelled arrow between two boxes conveys that they are connected, which the reader already assumed. |
| 5. Names match the code exactly | `admet-core`, not "Core". `/predict`, not "prediction endpoint". A diagram that renames things forces the reader to hold a translation table. |
| 6. Requirement IDs appear where a figure discharges one | E.g. the 128-atom rejection on Fig 7.5 is annotated `FR-04`. This is what makes the figure usable from [`04-traceability.md`](../04-traceability.md). |
| 7. One direction of flow per figure | Left-to-right or top-to-bottom, chosen and kept. A figure with arrows going both ways across the middle takes three times as long to read. |
| 8. Legend on any figure with more than three shape or colour classes | If it needs no legend, it must not need one — do not add a decorative legend to a two-shape figure. |
| 9. Caption states what the reader should conclude | "Figure 7.5: single prediction, cache miss path" is a title. "…showing that the featuriser runs once per molecule, before the cache is consulted" is a caption. |

Rule 2 is the one most often broken by accident, because red is the obvious choice
for the interesting box. The cost shows up when a second interesting box appears in a
different colour and the reader spends a minute deciding whether the difference means
something.

## 5. Export standard

Non-negotiable, because a diagram that is illegible in print has not been drawn.

- **SVG wherever the target supports it** — GitHub Markdown, the Typst report, and
  the web docs all do.
- **PNG at 300 DPI when raster is unavoidable.** Not 72, not "whatever the export
  dialog offered". At 96 DPI a diagram is fine on screen and mush on paper, and the
  report is marked on paper.
- **Minimum body text 9 pt at final printed size.** Check by printing one page, not
  by zooming. A C4 container diagram scaled to fit a portrait A4 column is the usual
  offender.
- **Commit both the source and the export.** The source so it can be edited; the
  export so the report builds on a machine without Excalidraw. Both live in this
  directory; `.gitattributes` marks `*.excalidraw` and `*.svg` as text.
- **Filename = the register number**, e.g. `05-predict-seq.mmd` and
  `05-predict-seq.svg`. So the figure, its source and its row here are one `ls` apart.

## 6. Checklist before a diagram is considered done

Copy this into the pull request that adds it.

- [ ] Its row in §2 is real: the file has the registered name, in the registered tool
- [ ] The `02-design.md` §2 specification for it was read, including "the mistake to avoid"
- [ ] All nine §4 rules hold — walked, not assumed
- [ ] Every arrow labelled; every name matches the code
- [ ] Requirement IDs annotated where the figure discharges one (rule 6)
- [ ] SVG (or 300 DPI PNG) exported and committed beside the source
- [ ] Printed one page: nothing under 9 pt, nothing illegible
- [ ] Caption states a conclusion, not a title
- [ ] If it shows measured data: regenerated by `just diagrams` from `results/`, not hand-drawn
